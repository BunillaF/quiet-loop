Below is a working currency arbitrage detector — the same algorithm I built for a university assignment, running live on real exchange-rate logic. It finds the one loop, out of many, where the numbers don't add up.

Five currencies. One quiet loop.

Each arrow below is a real exchange rate. Most round-trips lose you a fraction of a cent to spread — invisible, forgettable. Somewhere in this graph, one loop doesn't. Bellman-Ford finds it by checking every path for a cycle that multiplies to more than one.

This is a small example — five currencies, a handful of rates. But the principle scales: the same search, pointed at power plans, insurance premiums, or grocery pricing, finds the same kind of quiet leak. That's the work I want to keep doing.

Who I am underneath the code

I grew up in Auckland with a controller in my hands. Long before I understood what a variable was, I was rebuilding levels in game editors just to see if I could make them run smoother, load faster, feel a little more considered. That curiosity — is there a better way to do this? — has never really left. It's just changed shape as I've grown up.

By the time I got to my Computer and Information Sciences degree, I noticed the same question sitting behind everything I found interesting: not "does this work," but "does this work as well as it could." That's the thread running through the two projects on this page. In Java, I built a currency arbitrage detector using the Bellman-Ford algorithm — a small tool that catches an inefficiency in exchange rates that a person would otherwise have to hunt for manually, and finds it instantly. In Unity, on a team project called WhackANote, I owned the backend: the leaderboard and save data that make a game feel alive rather than disposable. Different domains, same instinct — find the part of a system that's quietly wasting someone's time, and fix it properly.

I don't yet know exactly which door that instinct will walk through professionally. Game development and software engineering both genuinely pull at me, and I've stopped seeing that as indecision. They're the same craft — building systems that respect the person using them — aimed at different audiences. What I want, more than a fixed job title, is to keep working on problems where "smarter" is actually measurable: faster, fairer, less wasteful, more alive.

I'm applying for this scholarship because that kind of work takes room to explore, and financial pressure is the fastest way to lose that room. Right now I balance coursework with actually building things — not just for marks, but because I want to be good at this by the time I graduate, not just qualified. A scholarship like this buys back the hours I'd otherwise spend worrying about fees, and gives them back to projects like the one running above.

New Zealand has a particular kind of usefulness. We're small enough that one good idea, built by one person willing to sweat the details, can genuinely move something forward — a business, a service, a habit people rely on. I'm not chasing something abstract or global; I want to build things that make life here quietly, measurably better, the same way a well-placed leaderboard or a well-found arbitrage loop does — unglamorous, and completely worth doing properly.

That's who I am underneath the code: someone who notices the loop nobody's checked yet, and can't quite leave it alone.

I want to spend a career finding the loops nobody's checked yet — and building the tools that check them automatically, for people who'll never see the code underneath.

— Finn
