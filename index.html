Most inefficiency hides in plain sight.

Below is a working currency arbitrage detector — the same algorithm I built for a university assignment, running live on real exchange-rate logic. It finds the one loop, out of many, where the numbers don't add up.

The demo

Five currencies. One quiet loop.

Each arrow below is a real exchange rate. Most round-trips lose you a fraction of a cent to spread — invisible, forgettable. Somewhere in this graph, one loop doesn't. Bellman-Ford finds it by checking every path for a cycle that multiplies to more than one.

watching for a loop that shouldn't exist…

This is a small example — five currencies, a handful of rates. But the principle scales: the same search, pointed at power plans, insurance premiums, or grocery pricing, finds the same kind of quiet leak. That's the work I want to keep doing.

A smaller example

The same instinct, at a different scale

I care about this at every size. In WhackANote, a rhythm game I built with a small team, my job was the part players never think about — the leaderboard and save data underneath the music. Getting it right meant a bug I hit could be traced back to Unity's own package rather than my code, and choosing to hold at an older, stable version rather than ship something fragile. Nobody claps for a leaderboard that just works. But it's the same care as the arbitrage loop above: find the thing that's quietly wrong, and fix it properly.

The written statement

Who I am underneath the code

I grew up in Auckland with a controller in my hands. Long before I understood what a variable was, I was deconstructing and seeing how the levels worked, seeing how things interacted with each other. That curiosity, unyielding- is there a better way to do this? It hasn't really left. It's just changed shape as I've grown up.

By the time I got to my Computer and Information Sciences degree, I noticed the same question sitting behind everything I found interesting: not "does this work," but "does this work as well as it could." This is the common theme between these two projects that are mentioned below.

In Java, I created a currency arbitrage detector using the Bellman-Ford algorithm, a small utility that detects an inefficiency in exchange rates that a person would normally have to seek out manually.

In Unity, as part of a team project named "WhackANote," I handled the backend, which consisted of the leaderboard and save file functionality that brought life into a game. Both in different contexts, but the same principle: detect the inefficiency in a system that takes someone's time and improve it.

I don't yet know exactly which profession I wish to pursue. Game development and software engineering both pull at me, and I've stopped seeing that as indecision. They're the same craft, building systems that respect the person using them, aimed at different audiences. What I want, more than a fixed job title, is to keep working on problems where "smarter" is actually measurable: faster, fairer, less wasteful, more alive.

I'm applying for this scholarship because that kind of work takes room to explore, and financial pressure is the fastest way to lose that room. That balance is tighter than it looks. Both of my brothers are autistic, and one also has epilepsy, so a real part of my week goes into looking after them, which narrows how much paid work I can take on alongside my degree.

Right now I balance coursework with actually building things, not just for the marks, but because I really want to be good at this by the time I graduate, not just qualified. A scholarship like this buys back the hours I'd otherwise spend worrying about fees, and gives them back to projects like the one running above.

There is a unique utility value associated with New Zealand. Because of our size, one great idea, created by one person who knows how to sweat the details, can actually do something tangible to improve a business, a service, or a practice that people depend upon. I don't think about doing something grandiose or on a worldwide scale; rather, I want to create something that improves this place in an incremental and practical way, the same way a well-executed leaderboard or a well-discovered arbitrage loop would.

That's what I am behind all the code: a person who can't help noticing an untapped, quiet loop.

I want to spend a career finding the loops nobody's checked yet — and building the tools that check them automatically, for people who'll never see the code underneath.

— Finn
